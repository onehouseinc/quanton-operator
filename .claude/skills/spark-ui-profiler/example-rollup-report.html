Likely bottleneck

A hot key in the customers join (likely). In stage 10 the slowest task, task 945 on executor 5, ran 297 s and read 758 MiB of shuffle data; the median task ran 25.2 s on 58 MiB, so it held 13× the data of a typical task. The join hashes rows by customer_id, and customer_id = 0 (guest checkout) holds about a fifth of the fact rows, which is consistent with one partition of that size. The task also spilled 742 MiB to disk, and its peak execution memory reached 3.5 GiB against about 1.2 GiB per task slot, so the spill follows from the skew rather than from the partition count. AQE split the products join but not this one: it does not split a skewed partition when the GROUP BY customer_id right after it would need another shuffle. A slow node is unlikely, since the other tasks on executor 5 ran at the median. Verify on the stage 10 page: Summary Metrics, Shuffle Read Size and Duration, max against median.

The products join shuffles the whole fact table (possible). The product columns come to about 40 MiB, above the 10 MiB broadcast threshold, so Spark shuffled 1.02 billion fact rows (9 GiB compressed) for stage 5 instead of broadcasting the small side.

What to change

--conf spark.sql.adaptive.forceOptimizeSkewedJoin=true   # stage 10: let AQE split the customer_id=0 partition
--conf spark.sql.autoBroadcastJoinThreshold=128m          # stage 5: broadcast products instead of shuffling fact

In the SQL, JOIN /*+ BROADCAST(products) */ does the second without a global setting; for the first, join the customer_id = 0 rows on their own path and UNION ALL. Try the configs first. The next run must show stage 10 with more than 24 tasks, a slowest task near the median, spill near zero, and a BroadcastHashJoin in place of the first SortMergeJoin.

What would not help

More executors or more memory: 23 of 24 slots had nothing to run for most of stage 10, and the slow task's data would still land on one slot. Raising spark.sql.shuffle.partitions does not split a single key either. The UI cannot show which key the slow partition holds; a GROUP BY customer_id count on the fact table would confirm it.
